## Q4, explained properly

Every website, in the end, is just three things the browser understands: **HTML** (the structure), **CSS** (the looks), **JavaScript** (the behavior). The only question is *how the code is written and checked* before it becomes those three things. You will never operate any of these tools yourself — DeepSeek does. The difference is how reliable its work is.

**Option A — one hand-written file, no tools.** The app is written directly as one final `index.html`. Like writing a book straight into its printed form, no editor, no proofreader. Zero setup. But once the app grows (editor, stats, quartets later), that file becomes a 2,000-line tangle, and nothing catches mistakes — a typo can silently corrupt your stack data or scoring.

**Option B — small workshop (my recommendation).** Three tools, one job each:
- **TypeScript** = JavaScript plus a spellchecker for code. It catches "you asked for the card's *positon*" or "this expected a number, got text" *before the app ever runs*.
- **Vite** = the packaging machine. It takes the many small source files and bundles them into the plain HTML/CSS/JS the browser needs. While developing, it shows a live preview that updates on every save. **Vite is not hosting** — GitHub Pages still hosts the finished files; Vite just prepares them.
- **Vitest** = automatic tests. Small checks like *"Mnemonica position 1 must be 4♣"* or *"a miss resets the streak"* that run in seconds after every change. This is the AI agent's safety net: when DeepSeek edits something, the tests instantly tell it if it broke anything.

Cost to you: a one-time free install of Node.js (~2 minutes), which the prompt will walk you through.

**Option C — B plus a UI framework (React/Svelte).** A prebuilt kit for managing screens and buttons. Worth it for big apps; overkill for this one. More moving parts, more for the agent to get wrong, bigger download.

| | A: one file | B: workshop | C: framework |
|---|---|---|---|
| Setup you do once | none | install Node.js | install Node.js |
| Catches agent mistakes | nothing | types + tests | types + tests |
| Adding modes later | painful | clean | clean |
| Complexity | lowest | small | highest |

For an AI-built app where **wrong stack data = ruined training**, B's safety net is the whole point.

## Licenses, explained

First, a clarification that matters: **all** of these licenses let anyone use, study, adapt, and even sell the code. "Viral" (copyleft) never restricts *using* — it only sets conditions on *sharing modified versions*. The real question is: when someone improves your trainer and shares it, must their improvements stay open too?

| License | Anyone free to use/adapt? | Must changes stay open? | The catch |
|---|---|---|---|
| **MIT** | ✅ | ❌ | Someone can fork it, improve it, and keep their version closed. Maximum adoption, zero guarantees back. |
| **Apache-2.0** | ✅ | ❌ | MIT plus patent-protection clauses. Same openness outcome, more legal machinery. |
| **GPLv3** | ✅ | ✅ when they *distribute* the app | The web-app loophole: **hosting** a modified website doesn't count as "distributing" — so someone can run an improved fork publicly and never share the code. |
| **AGPLv3** | ✅ | ✅ even when they only *host* it | Closes that loophole: anyone running a modified version as a website must offer its source to their users. Some companies avoid AGPL code — irrelevant for a magic trainer. |

For a web app specifically, GPLv3's promise is mostly illusory — hosting is exactly how web apps get shared. If "changes must remain under the same license" is what you want, **AGPLv3 is the one that actually delivers it**. If you'd rather have zero friction and don't care about forks staying closed, MIT.
